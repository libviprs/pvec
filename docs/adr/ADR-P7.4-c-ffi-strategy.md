# ADR P7.4: The C/FFI adapter strategy

Status: Proposed, 2026-10-25, for review. Decides issue #55 (P7.4). Builds on the facade (P7.1, #52), the
tessellation API (P7.2, #53) and the packed buffers (P7.3, #54). The recommendation is below; whether a C
header is worth having at all is the reviewer's call, and the measurements are here so that call has numbers
behind it.

## Context

Rust's data layout is not a stable ABI, so no `&Curve` and no `PvecReader` can be handed to a C consumer.
Whatever C sees has to be a small set of `extern "C"` functions over opaque handles and plain data, kept
in step with a header by some mechanism. That is work, it is surface the project then has to support, and it
only pays if somebody calls it. Today the consumers named in the issue tracker are `libviprs` (a Rust crate, so
it links `pvec` directly) and `libviprs/maplibre-pvec` (a browser, so it uses `pvec-wasm`). Nobody has asked
for C.

## Options

I measured four shapes on the same task: open a fixture from C and return its entity count. The fixtures are
the 22 canonical artifacts of the P2.4 generator (P8.1 does not exist yet), and each prototype is held to the
count the generator wrote down, 22 of 22 each. The prototypes are `spikes/p7-4-ffi`, throwaway, with their own
lockfile; `run.sh` there prints every number below, and the raw output of both runs is in `results/`.

* (a) a hand-written `extern "C"` facade over opaque handles with `#[repr(C)]` plain data only, and a header
  written by hand.
* (b) the same Rust code with a header that `cbindgen` 0.29 generates on every build.
* (c) no native C ABI in v1. Embedders use `pvec-wasm`, and native consumers link the `pvec` crate. The
  prototype is a Rust consumer that prints the same count.
* (d) a C-callable packed-buffer API that mirrors the P7.3 arrays: integer handles, four number arrays, no
  struct anywhere in a signature. It runs on top of `pvec_wasm::Runtime`, so it is the same contract.

Platforms: every number comes from a native machine, none from emulation. x86_64 is MARS, a Linux
container on `rust:1.99.0-bookworm` (gcc 12.2.0, glibc). arm64 is mercury, the same image as a native arm64
container. The counts and outcomes are identical on both; only the `.wasm` size differs.

| | (a) hand header | (b) cbindgen header | (c) no C ABI | (d) packed buffers |
|---|---|---|---|---|
| exported C symbols in the prototype | 3 | 3 | 0 (the `pvec-wasm` module has 17 entry points of ours and 84 of toolchain glue) | 8 |
| prototype opens the fixtures from C | 22 of 22, dynamic and static link | 22 of 22 | 22 of 22 from a Rust consumer | 22 of 22 |
| header written by hand | 20 lines, 3 declarations | 0 (70 generated) | none | 17 lines, 8 declarations |
| the Rust signature drifts from the header | silent: the C program still compiled and printed 18446744069414584321 where 1 is right | the C program no longer compiles (`-Werror=incompatible-pointer-types`) | no header | not measured; a hand header, so the same as (a) |
| a `#[repr(Rust)]` type can leak into a signature | yes | yes, and cbindgen writes an opaque `Vec_u8` into the header without complaint | no C surface | yes |
| and it is caught at compile time | yes, by `#![deny(improper_ctypes_definitions)]`: rustc says "extern fn uses type Vec<u8>, which is not FFI-safe"; without the `deny` it is one warning | the same lint | n/a | the same lint |

The `.wasm` of `pvec-wasm` is 466,775 bytes on x86_64 and 466,223 bytes on arm64 (no `wasm-opt`).

Projecting the surface: the facade snapshot has about 18 methods, and a caller needs roughly a dozen
constructors to build a `Curve`, because the enum's payloads are not `#[repr(C)]`. Candidates (a) and (b)
have to wrap each of those, one `extern "C"` function and one header line apiece, and every later facade
method adds one. Candidate (d) stays at about eight: the curves never cross the boundary, only the packed
arrays do.

## Decision

v1 does not ship a C header. Native consumers link the `pvec` crate and embedders use `pvec-wasm`, which is
candidate (c).

I picked it because nothing in the tracker needs C today, and each of the C shapes is real surface to keep:
(a) drifts silently, which is the worst property a boundary can have; (b) fixes the drift but still has to wrap
every constructor the facade needs, so its symbol count grows with the facade; (d) is cheap, but a second
public contract beside `docs/WASM_ABI.md` is still a contract. Shipping none costs nothing and closes
nothing: the prototypes for (b) and (d) exist and ran.

If a C ABI is wanted later, the path is (d), not (a) or (b). It is 8 symbols against a header of 17 lines,
the signatures hold only integers, `f64` and pointers to numbers (so there is no Rust layout to leak, and the
lint above refuses one if somebody adds it), and it reuses the contract and the tests of P7.3. A header
generated by cbindgen can replace the hand one once the symbol count passes about 16, which is where two
hand-kept declarations per change stop being a review item.

## Consequences

* Nothing to publish or version for C in v1. P8.7 records the deferral as a v1 non-goal.
* The no-Rust-layout rule for the deferred path is enforced by `#![deny(improper_ctypes_definitions)]` on the
  adapter crate plus a surface scan like the one `pvec-wasm` has for its exports; the header, if it appears,
  holds opaque pointers and `#[repr(C)]` plain data only.
* `spikes/p7-4-ffi` stays as the starting point. It is throwaway and is not built by the workspace.
* The prototype counted fixtures, not performance. Nothing here says a C call is cheaper or dearer than a
  `pvec-wasm` call.

## Reversal threshold

Ship a C header when a consumer that can link neither the `pvec` crate nor a WASM module is named in an
issue, with its toolchain and the number of entry points it needs. Then build (d), and if it needs more than
16 entry points generate its header with cbindgen instead of writing it. If a second consumer needs
curve-level calls (building a `Curve` from C, not reading packed arrays), reopen this ADR, because then
(d) is not enough and (b) with wrapped constructors is.
